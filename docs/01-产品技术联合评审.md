## 一、评审结论摘要

两份文档在**核心方向**上对齐良好：单向筹码经济、服务端权威、Redis 热状态 + MySQL 冷持久化、Bot GTO 补位、官方/私人双场次。但存在 **12 处文档矛盾**、**23 项待产品决策**、**18 项待技术细化**，若不先闭环，开发阶段将在边池结算、带入扣款、持久化时机、私人场权限流等模块反复返工。

**建议流程**：

```
Week 0（当前）: 联合评审 → 关闭待决策项 → 输出 v1.5 基准文档
Week 1+:        按 Phase 1 里程碑启动基础设施与核心引擎
```

## 二、文档矛盾与一致性修正（必须优先关闭）

| 2 | 文档版本号 | 正文 v1.4，页脚 v1.1 | v1.0 | 统一维护 CHANGELOG，页脚与正文版本一致 |

| 4 | 架构图 LB→MySQL | 架构图显示 Load Balancer 直连 MySQL | 文档明确 API/Room Server 访问 DB | **修正架构图**：删除 LB 到 MySQL 的直连线 |
| 5 | 私人场 Bot | PRD 明确「不支持 Bot」 | 架构未强调私人场 Bot 禁用 | 架构文档 Room Server 加入 `room_type` 分支校验 |
| 6 | 语音禁言 | PRD 提到「文字/语音禁言」 | 全文无语音功能规格 | **产品决策**：v1.0 仅文字聊天；语音列入 v2.x 或删除 PRD 中语音描述 |
| 7 | 支付渠道 | PRD 同时提到 USDC/World App、Apple IAP、Google Play | 架构仅写「支付网关」 | 需单独支付集成规格（见 `02-待决策事项清单.md` #P-07） |
| 8 | 游客试玩 | PRD 支持游客模式 | 架构 login API 未区分游客/正式账号 | 补充 `users.account_type` 及绑定转正流程 |

| 12 | 等级经验阈值 | 仅描述获取方式，无 Lv.1→100 曲线 | 无对应表结构 | 补充 `level_config` 配置表或公式 |

## 三、产品侧评审议程（Product Review Agenda）

> 以下议题需产品经理拍板，技术方可据此定 Schema 与状态机。

### 3.1 场次与匹配（P0 — 阻塞开发）

| 议题 ID | 问题 | 影响模块 | 建议默认值 |
|---|---|---|---|
| P-01 | 官方场每桌最多几人？最少几人开局？ | 房间模型、UI 座位布局 | **6 人桌，≥2 人可开局**（Heads-up 允许） |
| P-02 | 快速开始匹配半径：是否跨服/跨区匹配？ | 匹配服务 | v1.0 单区域匹配，不做全球合服 |
| P-03 | 动态带入上限「以此类推」的精确公式？ | 带入校验 | 当 ≥2 人筹码 > `100 × 2^n` 时，上限 = `100 × 2^(n+1)`，n≥0；无上限封顶 |
| P-04 | 官方场是否允许「观战」？ | 权限、UI | v1.0 **不允许**，仅 seated 玩家 |
| P-05 | 私人场最少/最多人数？ | 建房表单 | 2–9 人，房主可选 |

### 3.2 经济与合规（P0）

| 议题 ID | 问题 | 影响模块 | 建议默认值 |
|---|---|---|---|
| P-06 | 筹码是否只用整数？DECIMAL(18,2) 是否过度设计？ | DB、UI 显示 | **业务层仅整数**，DB 用 BIGINT 存储，避免浮点 |
| P-07 | v1.0 首发支付渠道优先级？ | 商城、合规 | MVP：**Apple IAP + Google Play**；Web 端 Stripe/USDC 作为 v1.1 |
| P-08 | 破产弹窗是否允许「试玩场」或 0 筹码旁观？ | 大厅流程 | **不允许**，必须充值或离开 |
| P-09 | 私人场 Re-buy 房主超时未审批？ | 私人场状态机 | 60 秒未响应自动拒绝 |
| P-10 | 运营赠送筹码是否区分「可提现/不可提现」？ | 经济模型 | **不区分**（筹码均不可兑换），但流水 type 需独立标记便于审计 |

### 3.3 社交与成长（P1 — 可并行，不阻塞 MVP）

| 议题 ID | 问题 | 建议 |
|---|---|---|
| P-11 | 好友上限？ | 200 人 |
| P-12 | 好友邀请进私人场：是否校验好友关系？ | 仅分享链接/房间号，不强制好友 |
| P-13 | Lv.1→100 经验曲线？ | 采用 `EXP(Lv) = 50 × Lv^1.5` 取整（见补充 Schema） |
| P-14 | 排行榜隐身：是否影响好友可见？ | PRD 已说明「好友列表仍可见」，✅ 确认 |
| P-15 | 牌桌文字聊天：全局 or 仅私人场？ | 官方场仅 Emoji 快捷语；私人场开放文字 |

### 3.4 Bot 与体验（P0）

| 议题 ID | 问题 | 建议 |
|---|---|---|
| P-16 | Bot 补位上限：一桌最多几个 Bot？ | 最多 **4 个 Bot**，至少保留 1 个真实玩家 |
| P-17 | Bot 每日亏损预算默认值？ | 全服 **500,000 筹码/日**，后台可调 |
| P-18 | Bot 被「看穿」后的客诉策略？ | 不提供 Bot 身份披露；客诉仅查回放 |
| P-19 | 真实玩家满桌后 Bot 「下一局离开」— 若 Bot 正在 All-in？ | **当前手牌结束后**再退，不中断牌局 |

### 3.5 风控与合规（P1）

| 议题 ID | 问题 | 建议 |
|---|---|---|
| P-20 | GPS 警告是否 v1.0 上线？ | 可选权限，默认关闭；后台仅记录 |
| P-21 | 冻结账号时桌上筹码如何处理？ | 立即强制 Sit Out，当前手牌结束后筹码退回账户并锁定 |
| P-22 | 私人场合规协议：开房时勾选 or 首次进入私人场入口？ | **申请权限时勾选**，存证 timestamp + IP |
| P-23 | 年龄限制 / 地区屏蔽？ | 产品/legal 确认；技术预留 `geo_block` 配置 |

## 四、技术侧评审议程（Tech Review Agenda）

> 以下议题需架构/后端/客户端负责人确认，输出到架构补充文档。

### 4.1 核心引擎（P0）

| 议题 ID | 问题 | 建议方案 |
|---|---|---|
| T-01 | 状态机选型 XState 运行在哪？ | Room Server 进程内，每桌一个 Actor |
| T-02 | 边池 + 抽水 + 奇数筹码分配顺序？ | 单元测试覆盖：先算边池 → 再扣 rake → 再分配，rake 从总 pot 扣 |
| T-03 | 并发行动（网络乱序）如何处理？ | 服务端 ActionQueue 串行化；客户端乐观 UI 可选，以服务端回包为准 |
| T-04 | 15 秒倒计时由谁驱动？ | 服务端 `action_turn` 携带 `deadline_ts`；客户端本地插值展示 |
| T-05 | Bot 决策超时？ | gRPC 调用超时 **800ms**，超时则 Bot Check/Fold |

### 4.2 数据与一致性（P0）

| 议题 ID | 问题 | 建议方案 |
|---|---|---|
| T-06 | Redis 宕机如何恢复？ | Redis AOF + 每手牌结束写 `hand_histories`；Room Pod 崩溃从 Redis 快照 + 最后 hand 恢复 |
| T-07 | 带入扣款幂等性？ | `lock:buy_in:{user_id}` + 客户端 `request_id` 去重 |
| T-08 | 筹码流水与余额一致性？ | `users.chips_balance` 仅作快照；审计以 `chip_transactions` SUM 为准，定时对账任务 |
| T-09 | hand_histories.actions_json 写入粒度？ | 每手牌 END_HAND 时一次性写入完整序列 |
| T-10 | 排行榜刷新？ | Redis ZSET 缓存，每 10 分钟从 MySQL 聚合刷新；周一 0:00 cron 重置 |

### 4.3 通信与安全（P0）

| 议题 ID | 问题 | 建议方案 |
|---|---|---|
| T-11 | JWT 有效期？ | Access 2h + Refresh 30d；WebSocket 连接时校验并支持 silent refresh |
| T-12 | WebSocket 鉴权？ | 连接 query/header 带 JWT；Room Server 与 API Server 共享 JWT secret 或走 introspection |
| T-13 | 底牌加密方案？ | 服务端内存持有；下发时 per-player 加密通道（Socket.io room）；Showdown 广播明文 |
| T-14 | IP 互斥实现层？ | Room Server join 中间件，查 Redis `room:{id}:ips` SET |
| T-15 | Rate Limit？ | API: 100 req/min/user；WS: 30 actions/min/user |

### 4.4 部署与运维（P1）

| 议题 ID | 问题 | 建议方案 |
|---|---|---|
| T-16 | Room Pod 路由 | Gateway 基于 `room_id` 一致性哈希；Redis 存 `room:pod:{room_id}` |
| T-17 | 单 Pod 200 桌如何验证？ | Phase 4 压测目标：P99 延迟 <100ms，CPU <70% |
| T-18 | 日志与追踪 | OpenTelemetry + 结构化日志；每手牌 trace_id = hand_id |
| T-19 | 对局回放存储 | actions_json 存 MySQL；大字段 >64KB 考虑 OSS 归档 |
| T-20 | CI 必测用例 | 边池(≥5 scenarios)、rake(no flop/flop)、动态 cap、带入幂等 |

## 五、MVP 范围确认（v1.0 交付边界）

### ✅ v1.0 必须交付

- 官方场完整对局（1/2 盲注、动态带入、5% 抽水）
- 用户系统（Apple/Google 登录 + 游客）
- 充值商城（Apple IAP + Google Play）
- Bot 补位（GTO 引擎联调）
- 基础反作弊（IP/设备互斥）
- 断线重连（State Snapshot）
- 后台最小集（用户查询、封禁、筹码流水查看）

### ⏸ v1.0 不做（移入 v1.5）

- 私人定制场
- 好友系统
- 排行榜 / 成就
- 对局回放 UI（后端可先写 hand_histories）
- 运营活动 CMS
- 自定义皮肤 / VIP

> **产品确认**：若商务要求私人场同步上线，需将 Phase 3 提前，MVP 周期相应延长。
